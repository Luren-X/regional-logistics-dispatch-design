# 系统架构多方案权衡与选型论证


---

## 1. 架构评估基准（源自非功能需求约束）

结合本系统“单一城市/都市圈区域物流”的业务定位，确立以下 5 项架构评估指标及权重：

1. **开发与学习成本（权重 25%）**：在有限实验周期与小型团队规模下，能否快速完成设计、联调与交付。
2. **运维与部署复杂度（权重 20%）**：服务器资源开销、配置管理与故障排查难度。
3. **模块解耦与可维护性（权重 20%）**：是否满足高内聚、低耦合，便于独立迭代调度算法或新增异常通知方式。
4. **并发与实时响应能力（权重 20%）**：能否满足 100 辆车高频 GPS 上报写入及 200 笔运单 3 秒内智能派单响应。
5. **未来平滑扩展性（权重 15%）**：若未来业务由单区域扩张至全国多省市，架构能否低成本演进。

---

## 2. 三套候选架构方案详述

### 方案 A：传统三层单体架构
* **方案描述**：将表现层、业务逻辑层、数据访问层打包为一个单一应用，所有请求（包括 GPS 轨迹入库、地图 API 调用、异常短信推送）均采用同步阻塞方式直接读写单一 MySQL 数据库。
* **核心优势**：技术栈最简单，本地调试与一键部署成本最低，天然支持数据库本地 ACID 事务。
* **主要缺陷**：
  * 模块边界模糊，耦合度高；
  * 车辆高频 GPS 上报与异常短信推送若全部同步阻塞主线程，在高峰时段极易拖垮核心下单与智能派单接口。

### 方案 B：全套分布式微服务架构
* **方案描述**：按 5 大子系统拆分为 5 个独立部署的微服务（如基于 Spring Cloud / Nacos / OpenFeign / Seata），每个服务独占一个物理数据库，跨服务业务通过分布式事务协调。
* **核心优势**：单服务可独立弹性伸缩（如单独给调度计算服务加机器），物理隔离彻底，适合大型全国性物流平台与数十人研发团队。
* **主要缺陷**：
  * **典型的“过度设计”**：引入注册中心、配置中心、链路追踪、分布式事务后，开发与运维复杂度呈指数级上升；
  * 网络序列化与跨服务 RPC 开销反而会增加单次派单的链路延迟，远超出区域级并发的实际需求。

### 方案 C（最终选定）：模块化单体 + 异步事件驱动混合架构
* **方案描述**：保持单一应用部署单元（简化部署与本地 ACID 事务），但在代码与逻辑架构内部严格按 5 大领域划分强隔离模块（**禁止跨模块直接访问数据库表，只能通过接口契约通信**）；同时引入 **Redis + RabbitMQ**，将高并发 GPS 实时定位、地图距离缓存以及在途异常多端告警全面异步事件化。
* **核心优势**：
  * **事务强一致**：一键派单涉及运单、车辆、任务单三表联动，直接复用数据库本地 ACID 事务，彻底规避分布式事务陷阱；
  * **性能与解耦兼得**：通过异步消息队列与 Redis GEO 完美化解高频 GPS 写入与异常推送瓶颈；
  * **渐进式演进**：由于模块内部边界已完全解耦，未来业务扩展至跨省高并发时，可将“智能调度引擎”或“在途监控”几乎零重构地剥离为独立微服务。

## 4. 附：数据存储子方案权衡

在确定总体架构后，针对“车辆高频 GPS 位置与核心运单数据如何存储”，同样进行了双方案对比：

| 对比项 | 备选方案 1：纯 MySQL 单一存储 | 备选方案 2：MySQL + Redis（GEO/锁）混合存储（选定） |
| :--- | :--- | :--- |
| **实时车辆位置查询** | 需在千万级轨迹表上做分组取最新记录，查询延迟随运行天数急剧恶化 | Redis `GEOADD`/`GEORADIUS` 内存级读写，毫秒级查出事故点周边 5km 内空闲救援车 |
| **防超载/防重复派单** | 依赖数据库行锁或表锁，并发派单时易引发死锁或锁等待超时 | Redis 分布式锁拦截并发冲突 + MySQL `version` 字段乐观锁兜底 |
| **综合结论** | 仅适合演示原型，无法支撑在途高频监控 | **选定方案 2**：MySQL 保障事务 ACID 与历史归档，Redis 保障实时空间检索与并发安全 |

## 5. 架构决策记录（ADR-001）与演进路线

* **最终决策**：采用 **方案 C（模块化单体 + 异步事件驱动 MQ）** 搭配 **MySQL 主从 + Redis 混合存储**。
* **两阶段演进路线**：
  1. **V1.0 区域落地期（当前设计）**：以模块化单体形态快速上线，验证同城/省内智能调度与异常改派闭环，运维成本最低。
  2. **V2.0 跨省扩张期（未来预留）**：当在线车辆突破 2,000 辆、日均运单突破 10 万单时，优先将计算密集型的 `智能调度引擎模块` 与写入密集型的 `车辆在途监控模块` 按既有接口契约独立拆分为微服务，实现无痛架构升级。
